# Optional local S3 recovery test

The S3 variant uses a separate Compose project and a private bucket served by
Silo, an actively maintained MinIO fork that publishes pinned ARM64 and AMD64
images. Upstream MinIO Community is source-only and the test could not pull
its former image. Silo's S3 API and bucket client let this test run with a
single additional service and no cloud credentials. [MinIO upstream](https://github.com/minio/minio) · [Silo upstream](https://github.com/pgsty/silo)

The archive uses its documented jclouds S3 provider with path-style bucket
access. The LDAP script points the S3 project's `fs1` descriptor at
`http://s3:9000`, selects the precreated `sphinx-dicom` bucket and preserves
the default object path format. The descriptor holds the local S3 credential
in the LDAP volume. The S3 API and console have no published host port.
[Archive S3 configuration](https://github.com/dcm4che/dcm4chee-arc-light/wiki/S3-Storage)

## Start

Prepare the base `.env` as in the README and add the two S3 values once.

```sh
if ! grep -q '^SPHINX_S3_ACCESS_KEY=' .env; then
  {
    printf 'SPHINX_S3_ACCESS_KEY=%s\n' "$(openssl rand -hex 12)"
    printf 'SPHINX_S3_SECRET_KEY=%s\n' "$(openssl rand -hex 24)"
  } >> .env
fi
docker compose down
s3() { docker compose -p sphinx-phase1-s3-demo -f compose.yaml -f compose.s3.yaml "$@"; }
bucket() {
  s3 exec -T s3 sh -ec '
    export MC_HOST_sphinx="http://$MINIO_ROOT_USER:$MINIO_ROOT_PASSWORD@127.0.0.1:9000"
    exec mc "$@"
  ' sh "$@"
}

s3 config --quiet
s3 up -d --wait ldap db s3
bucket mb --ignore-existing sphinx/sphinx-dicom
s3 exec -T ldap sh -s < config/dcm4chee/s3-storage.sh
s3 up -d --wait
.venv/bin/python scripts/demo.py ready
```

The S3 project's archive must first start after the bucket and LDAP descriptor
are ready. To repeat setup on an existing S3 project, stop its `arc` service
first. Never retarget the filesystem project's `fs1` descriptor after ingest.

## Verify bucket placement and recovery

Ingest a fresh fixture and use the printed run directory. The exact three
object keys for this study come from its PostgreSQL locations. Fetch those
keys directly from S3 and verify their objects against the source manifest.

```sh
.venv/bin/python scripts/demo.py ingest
run=data/run-REPLACE_ME
study_uid=$(.venv/bin/python -c 'import json, sys; print(json.load(open(sys.argv[1]))["study"])' "$run/manifest.json")
objects=$(mktemp -d "$run/s3-objects.XXXXXXXX")
s3 exec -T db psql -X -U pacs -d pacsdb -At -v ON_ERROR_STOP=1 -v study_uid="$study_uid" <<'SQL' > "$run/s3-keys.txt"
SELECT l.storage_path
FROM location l
JOIN instance i ON i.pk = l.instance_fk
JOIN series se ON se.pk = i.series_fk
JOIN study st ON st.pk = se.study_fk
WHERE st.study_iuid = :'study_uid' AND l.storage_id = 'fs1'
ORDER BY i.sop_iuid;
SQL
bucket ls --recursive sphinx/sphinx-dicom
n=0
while IFS= read -r key; do
  n=$((n + 1))
  bucket cat "sphinx/sphinx-dicom/$key" </dev/null > "$objects/$n.dcm" || break
done < "$run/s3-keys.txt"
.venv/bin/python scripts/demo.py verify "$run" "$objects"
```

Restart the archive service alone, wait for readiness and run the same
source-loss and receiver test as for the filesystem variant. The test client
retrieves over DICOMweb even if direct S3 downloads exist on disk.

```sh
s3 restart arc
s3 up -d --wait
.venv/bin/python scripts/demo.py ready
.venv/bin/python scripts/demo.py restore "$run"
s3 down
```

Shutdown preserves the S3 project's bucket, catalogue and configuration
volumes. Direct reads of the test objects demonstrate their DICOM content.
A fresh-catalogue reconstruction or full archive disaster recovery remains a
separate test.
